### Rendering

5. **[RENDERING] Use DOM with one CSS `transform` on a single board container; reject canvas/WebGL outright and add no dependency** — canvas is disqualified on three independent grounds, not just performance: MDN is explicit that `<canvas>` content is not exposed to assistive technology and "must be made accessible by providing fallback text… Providing useful fallback text or sub DOM adds accessibility to an otherwise non-accessible element" — a per-node transcript plus a live composer would have to be duplicated into a shadow DOM tree, i.e. build the DOM version anyway; a canvas also cannot host a real `<textarea>`, text selection, or copy-paste out of a transcript, all of which a chat surface needs. On the library question: `@xyflow/react` and every node-editor of that family require React, and this package has exactly two runtime dependencies (`@dg/common`, `kokoro-js`) with no React anywhere — pulling React + react-dom into a vanilla WXT extension for one page is a bundle and convention cost far past what the feature justifies. A generic pan/zoom library solves only the ~150 lines of pointer arithmetic and solves neither node dragging nor position persistence nor the keyboard alternative, which are the parts that actually carry risk. Hand-roll it; this is the YAGNI answer and the repo-conventions answer at the same time.

6. **[RENDERING] Enumerate what actually degrades at 10+ nodes, and mitigate the transcripts rather than the transform** — a single transformed container with 10-30 absolutely-positioned children is not the bottleneck; N live transcripts each appending DOM forever is. Concretely: (a) cap retained transcript DOM per node and mount transcript content lazily — only for nodes intersecting the viewport or focused — using `IntersectionObserver`, so a 20-node board is not 20 growing scroll containers; (b) apply `contain: layout paint` per node so one node's reflow does not invalidate the board; (c) set `will-change: transform` on the board **only during** an active pan/zoom gesture and remove it on `pointerup` — leaving it on N nodes permanently allocates a compositor layer each and is the classic way this pattern runs out of GPU memory; (d) drive pan/drag updates from one `requestAnimationFrame` write per frame rather than writing `transform` inside the `pointermove` handler; (e) accept that text is resampled at fractional zoom scales and either clamp zoom to a small set of steps or accept the softness — this is a layout decision worth putting in front of the human at verdict time, not an implementation detail.

7. **[RENDERING] The board chrome must live outside the transformed subtree — verified** — MDN: fixed positioning's containing block is the viewport "unless any ancestor has `transform`, `perspective`, or `filter` property set to something other than `none`… which then causes that ancestor to take the place of the element's containing block", and "when the `will-change` property is set to `transform`, a new containing block is established." So the create-chat button, the `dg:start` banner, any zoom/fit controls and any focus-recovery affordance must be siblings of the transformed board, not descendants — otherwise they scale and drift with the board and their `position: fixed` silently resolves against it. This interacts with finding 6(c): switching `will-change` on for a gesture would move the containing block mid-interaction if the chrome were nested.

8. **[RENDERING] Set `touch-action: none` on the board and use non-passive `wheel` handling, with explicit target discrimination against the transcript scrollers — verified** — MDN: "By default, panning (scrolling) and pinching gestures are handled exclusively by the browser. An application using Pointer events will receive a `pointercancel` event when the browser starts handling a touch gesture", and `touch-action` "should… ensure the browser knows the intent of the application before any event listeners have been invoked." Three concrete consequences the plan does not mention: (a) without `touch-action: none` a trackpad/touch pan will die mid-gesture with `pointercancel`; (b) the zoom handler must call `preventDefault()`, which requires a non-passive `wheel` listener registered with `{ passive: false }`, and must intercept `ctrlKey`-modified wheel events since that is how browsers deliver pinch-zoom; (c) a wheel over a node's transcript must scroll that transcript and must **not** zoom the board — that discrimination (hit-test the event target against the scroll container, or require a modifier for zoom) is a real behavioural decision that belongs in the engineering checklist, because getting it wrong makes every attempt to read a long transcript zoom the board instead.

9. **[SHADOW DOM] `demo-tour.ts`'s shadow-root isolation does not apply here, and using it would break this slice's own theme requirement — verified twice over** — `wxt`'s declaration is `createShadowRootUi<TMounted>(ctx: ContentScriptContext, options)`: it takes a `ContentScriptContext`, so it is a content-script-only API and simply is not callable from an extension page. `demo-tour.ts` and `picker.ts` need it because they paint over arbitrary third-party pages and must not inherit or leak styles; `entrypoints/chat/` is a first-party extension page exactly like `review/` and `options/`, with no foreign CSS to defend against. More decisively, MDN on shadow DOM: "The page CSS does not affect nodes inside the shadow DOM" and "styles defined in the shadow DOM tree are scoped to that tree, so just as page styles don't affect elements in the shadow DOM…" — putting nodes in a shadow root would make `style.css`'s `.panel`, `.btn`, `.field`, `.sec-h`, `.note`, `.status` classes unreachable, which is precisely what this slice is required to style from. Recommend an explicit "no shadow root on this page" note so the demo-tour precedent is not copied by reflex.

### Theme

10. **[THEME — must resolve before build] `style.css`'s `body` rule constrains every page that imports it to a 42rem centered column; the board root must be `position: fixed; inset: 0` rather than a change to `style.css`** — the built output confirms the rule is global and unconditional: `body{max-width:var(--container-2xl);padding-inline:calc(var(--spacing)*5);padding-top:calc(var(--spacing)*10);padding-bottom:calc(var(--spacing)*16);font-family:var(--font-mono);background:var(--bg);color:var(--ink);min-height:100vh;margin-inline:auto}`. An infinite pan/zoom surface inside a 672px centered column with 40px/64px vertical padding is not the design. Slice 6 **cannot** fix this at the source: `style.css` lives under `pkg/extension/entrypoints/options/**`, which is slice 9's glob. Taking the board out of flow with `position: fixed; inset: 0; overflow: hidden; touch-action: none` sidesteps the rule entirely with no shared-file edit and no scrollbar (Tailwind's preflight sets `box-sizing: border-box`, so `min-height: 100vh` plus padding still resolves to 100vh on an otherwise-empty body). Recommend this over asking slice 9 to make the `body` rule opt-in — but it needs to be written down, because it is not what a page following the `review/` template would naturally do.

11. **[THEME — confirmed] `style.css` is importable from a second entrypoint with zero duplicated Tailwind output — verified in the built artifact** — `.output/chrome-mv3/options.html` and `review.html` both link the *same* `/assets/style-C4XOYaif.css` (13,352 bytes, one file, the only CSS in the build), because `review/main.ts` imports the identical module (`import "../options/style.css"`). So `entrypoints/chat/main.ts` doing the same reuses that chunk. The caveat is on slice 6's own new rules: a *second* CSS file cannot use `@apply` unless it can see the Tailwind context, and adding a second `@import "tailwindcss"` would emit a second full Tailwind build. Tailwind v4's answer is the `@reference` directive — "import theme variables and utilities for use with `@apply` without including the actual styles in the output." Recommend `entrypoints/chat/style.css` open with `@reference "../options/style.css";` (or drop `@apply` entirely and write plain CSS against `var(--accent)` etc., which the docs note is faster anyway), with `chat/main.ts` importing both stylesheets. Either way the palette stays single-sourced and the token requirement is met by construction.

12. **[THEME] `ui-helpers.ts`'s `ACCENT = "#6ea8fe"` should stay as-is and slice 6 must not import it; the `style.css` tokens win for this page** — the inconsistency is real (`#6ea8fe` matches neither `--accent` `#0891b2` light nor `#00f0ff` dark) but it is not slice 6's to fix. `ACCENT` has exactly two consumers, `demo-tour.ts:2010` and `picker.ts:200`, both shadow-root overlays on third-party pages where — per finding 9's verification — the page's stylesheet and therefore its custom properties are unreachable; they need a literal. And `## Scope`'s Excluded list bars "any change to how the demo tour, recorder, prototype, or tab-grouping features work." Two consequences: (a) slice 6 imports nothing from `ui-helpers.ts` — note that its other export, `createEl(tag, style)`, exists to *apply inline styles*, which is the opposite of this slice's convention; (b) the "no hard-coded hex colors outside `style.css`" criterion must be **scoped to slice 6's own files** (`entrypoints/chat/**`, `chat-canvas.ts`, `chat-node.ts`), or it fails on day one against the pre-existing `ACCENT` — and note `style.css` itself contains `color: #000` in `.navbtn:hover` and `.btn:hover`, which the current wording permits but a sloppier implementation of the test would not. Implement it as a source-text scan in a spec, not a computed-style assertion: `.stylelintrc.json` is `{"rules":{}}` and no `stylelint` script exists (`lint` is `tsc --noEmit`), so there is no lint hook to carry it.

### Accessibility

13. **[A11Y — escalate] Free-drag positioning needs a *non-drag pointer* alternative as well as a keyboard path, and the plan promises only the keyboard half** — WCAG 2.2 SC 2.5.7 Dragging Movements (Level **AA**) is normative: "All functionality that uses a dragging movement for operation can be achieved by a single pointer without dragging, unless dragging is essential or the functionality is determined by the user agent and not modified by the author", and it "operates independently from keyboard requirements… meeting keyboard requirements doesn't automatically satisfy this criterion." Node repositioning on a canvas is not plausibly "essential" (unlike, say, freehand drawing), so an alternative is required. The efficient answer satisfies both axes with one mechanism: a per-node **Move** control that enters a move mode where arrow keys nudge / Shift+arrows jump / Enter commits / Escape cancels, plus click-to-place on the board while in move mode. Recommend adding this as an engineering bullet and a testing criterion. Options if the human disagrees: (a) build the move mode as described; (b) declare dragging non-essential-but-unsupported and make position a non-drag affordance only; (c) accept a documented AA failure. Recommend (a).
   **⚑ RATIFY:** does slice 6 additionally need a **parallel linear (non-spatial) view** of sessions — a plain list of nodes, same data, no coordinates? A spatial free-position surface conveys its primary information (which chat is where, relative to which) through geometry that no screen reader can render, and "focus, move between, and close any node" is reachability, not equivalence. Options: (a) no linear view — keyboard traversal over the canvas only, accepting that the spatial arrangement itself is not conveyed; (b) a linear view as a toggle on the same page, sharing `chat-node.ts` (roughly the 6a sub-slice of finding 4 with its flow layout kept and exposed rather than replaced — the cheapest version, since 6a builds it anyway); (c) the linear view as the *only* keyboard surface, with the canvas marked `aria-hidden` and treated as a pointer-only presentation of the same list. Recommendation: **(b)**, because the proposed 6a/6b cut produces it as a by-product rather than as new work — but it is a scope addition and a product call, not a slice-6 engineer's decision.

14. **[A11Y] Do not use `aria-grabbed` / `aria-dropeffect` — verified deprecated** — MDN: "The `aria-grabbed` property is expected to be replaced by a new feature in a future version of WAI-ARIA and is considered deprecated", and `aria-dropeffect` is deprecated alongside it. MDN also cautions that "ARIA does not enable accessible functionality. ARIA only conveys the intended behavior of your functionality." Announce move-mode state and the committed position through a `role="status"` live region driven by the move mode of finding 13, using text a person can act on ("Moving node 2 of 4. Placed."), not a deprecated state attribute.

15. **[A11Y] Specify the focus model, and make focus drive the pan — it is also the honest answer to "a node dragged off-view remains reachable"** — three things the plan leaves open and a spatial surface cannot survive without: (a) **traversal order** — a free-position canvas has no reading order, so declare one (session creation order is the only stable choice; sorting by coordinates makes the tab order jump every time a node moves) and use a roving `tabindex` across nodes so Tab moves between nodes while arrow keys or a documented key moves *into* a node's transcript and composer — otherwise Tab wades through every message of node 1 before reaching node 2; (b) **pan-to-focused-node on `focusin`**, which makes off-view nodes reachable by construction and satisfies that criterion without inventing a separate recovery affordance; (c) **a live-region policy** — per-node `aria-live` on 10 live sessions is an announcement storm, so recommend only the focused node's transcript being live, other nodes surfacing arrivals through the unread count `chat-sessions.ts` already tracks (slice 5's finding 2), and the NEEDS YOU badge carrying a `role="status"` text label since a CSS pulse conveys nothing to a screen reader and nothing at all under reduced motion.

### Testing feasibility

16. **[TESTING] happy-dom has no layout engine — verified empirically — so every geometry criterion must be tested against exported pure functions, not rendered output** — probed in this package with `bun test`: a `div` with `style.width = "200px"; style.height = "100px"` appended to `document.body` returns `getBoundingClientRect()` `{w:0,h:0,x:0,y:0}`, `offsetWidth` `0`, and `clientWidth` `0`. `PointerEvent`, `WheelEvent`, `setPointerCapture`, `elementFromPoint`, `ResizeObserver` and `requestAnimationFrame` all exist as functions, but `elementFromPoint` and any hit-test built on rects are meaningless without layout. Practical consequence for `chat-canvas.ts`: export the arithmetic — `clampScale`, `clampPan`, `screenToBoard`/`boardToScreen`, `applyDragDelta`, `isNodeInView` — as pure functions over an injected viewport size, and let the spec drive *those*. Synthesised `pointerdown`/`pointermove`/`pointerup` sequences can still prove the state machine (drag starts, deltas accumulate, `pointercancel` aborts cleanly, capture is released) as long as no assertion reads a rect. Whatever remains — that the transform visually lands where the math says — is a browser check, not a `bun test`; recommend saying so rather than letting a green suite imply visual correctness.

17. **[TESTING] `prefers-reduced-motion` is mechanizable, but only if the implementation reads it from JS — verified empirically both ways** — happy-dom exposes `happyDOM.settings.device.prefersReducedMotion` (default `"no-preference"`), and setting it to `"reduce"` — either via the `Window` constructor's `settings` or by mutating `settings.device.prefersReducedMotion` after construction — flips `matchMedia("(prefers-reduced-motion: reduce)").matches` to `true` (and `no-preference` to `false`). So the criterion is testable. But if reduced motion is honoured *only* in a CSS `@media` block, no `bun test` can observe it: stylesheets imported through Vite are not applied under `bun test` at all, and `getComputedStyle` only resolves what was set inline (verified: an inline `--x: #00f0ff` with `color: var(--x)` does compute to `#00f0ff`, so the resolution machinery works — there is simply no stylesheet). Recommend the board read the query through an injectable seam (default `window.matchMedia`, mirroring `registerProto`'s `options.browserApi` pattern that slice 4's finding 10 also recommends) and reflect it as `data-motion="reduced"` on the board root, with the CSS `@media` block kept as belt-and-braces; the spec then asserts the attribute and that no easing/pulse timer was scheduled. Also subscribe to the query's `change` event — a user flipping the OS setting with the canvas open should take effect without a reload.

### Where position state lives

18. **[STATE] `chrome.storage.local`, keyed `chat_pos:<sessionId>`, pruned on load inside `chat-canvas.ts` — no undeclared slice dependency, but the persistence promise is weaker than it reads** — the repo precedent is exact: `demo-tour.ts` uses `demo_edit:${tabId}` / `demo_pending:${tabId}` and `demo-recorder.ts` uses `storage.local` keys, all `<feature>_<thing>:<id>`. `storage.sync` is wrong (`lib/config.ts`, slice 9's file, and per the `## Code Structure` asset-directory decision, machine-specific values do not belong there — a coordinate set for sessions that exist on one host is meaningless on another). `storage.session` is wrong because it is memory-only and dies with the browser, defeating "a reload restores the arrangement" across a browser restart. Daemon-side persistence would be defensible but is *not* reachable inside slice 6's files: the `sessions` table is slice 3's `src/store/**`, a new frame type is slice 1's `chat-format.ts`, and a new HTTP endpoint is slice 2's `src/server/**` — so choosing the daemon silently makes slice 6 depend on three slices it does not declare. Two things to write down with the `storage.local` choice: (a) **prune on load** — drop keys whose `sessionId` is absent from the current session list, inside `chat-canvas.ts`, since the cleanup precedent (`registerTourState`'s `tabs.onRemoved` sweep) lives in a background file slice 6 does not own, and without pruning this store grows one dead key per session forever; (b) **the promise only holds within one daemon lifetime** — `sessionId`s are minted per registration, so after a daemon restart (which slice 5's finding 8 shows also changes the port) every saved position is orphaned and the board opens at defaults. If "restores the arrangement" is meant to survive a restart, the key must be something stable — session `cwd` plus agent identity — which requires those fields to be present on the in-page session object and therefore a slice-1/5 change. Recommend keying on `sessionId` and narrowing the criterion to a page reload, and escalating if the stronger promise is intended.

### Cross-slice gaps and disjointness

19. **[DEPENDENCY — must move] The `$`/`@` composer affordances cannot be built in slice 6; move that bullet and its criteria to slice 8** — slice 6's "Render the composer's `$` and `@` affordances against the manifest published on connect" depends on a manifest that does not exist yet: slice 7 publishes it (`recv`/`send`/`status`/manifest ingestion, `depends_on: [2,3]`) and slice 8 owns the completion module (`lib/features/chat-autocomplete.ts`, `depends_on: [7]`). Slice 6 is `depends_on: [5]` and must land before slice 9 (`depends_on: [3,6]`), so it is ordered *ahead* of both. There is also a live responsibility overlap: slice 6 renders "affordances", slice 8 drives "completion in the composer" — two slices editing the same composer with no stated seam. Recommend slice 6 ship a plain composer that exposes a documented mount point / input element, and slice 8 attach autocomplete to it; drop the manifest bullet and "Autocomplete offers only manifest entries" stays where it already is, in slice 8.

20. **[COMPLETENESS] Slice 6 owns two distinct zero-states, and only one is in its criteria — the other is currently an acceptance criterion on slice 4, which cannot satisfy it** — "no session registered at all" (nothing in `chrome.storage.session`, e.g. the toolbar action clicked before `dg:start` ever ran) is a different state from "session known, daemon unreachable" (slice 5's `daemon-not-running`), and they want different copy: the first says run `dg:start`, the second says the daemon that *was* there has gone. Slice 4's AC — "Given no registered session, when the toolbar action is clicked, then the chat page explains that `dg:start` must be run" — is a slice-6 deliverable sitting on slice 4's checklist; slice 4 does not own `entrypoints/chat/**` and is ordered before it, so slice 4 will ship a toolbar action pointing at a page that does not exist until slice 6 lands. Harmless inside a single-PR bundle, but the criterion should move. Related and worth stating: the `/chat.html` URL string will live in slice 4's `lib/background/chat.ts` while the page lives in slice 6's glob — name it once and note the coupling. Slice 9's finding 5 raises the same portless-first-run problem for the options page, so both pages need a first-run story; they are not the same story and should not be assumed to share code.

21. **[COMPLETENESS — escalate] "Closing a node" is undefined, and the plan uses it two different ways** — the engineering bullet says "focusing, moving between, and **closing** nodes must not require a pointer" and a testing criterion says the board "removes a node when its session closes". But slice 9's finding 10 establishes that no slice defines a session-end trigger at all: a dropped socket is explicitly not an end (slice 5 reconnects), slice 7 has `spawn` but no close verb, and the only unambiguous end is the daemon exiting. So does the close control (a) remove the node from the board while the session stays alive on the daemon — a purely local, slice-6-internal action, in which case reopening the page brings it back and the control is misleadingly named; or (b) end the session on the daemon — which requires a frame type (slice 1) and daemon handling (slice 2/7) that no slice scopes? **⚑ RATIFY:** which does "close a node" mean — hide locally, or end the session? Options: (a) local dismiss only, renamed accordingly, with a way to bring a hidden session back (slice-6-internal, zero cross-slice cost); (b) a real session-close frame plus daemon handling, added to slices 1 and 2/7; (c) drop the close affordance from this slice. Recommendation: **(a)** for this bundle — it keeps slice 6 inside its own file boundary — with (b) deferred, since a real close is also what slice 9 needs to make "ending a session removes its staged assets" a distinct guarantee from its startup prune.

22. **[DEPENDENCY] Slice 6 inherits three unresolved slice-5 escalations and cannot satisfy its own criteria until they land** — recorded here so a checkpoint audit does not read them as slice-6 failures. (a) Slice 5's finding 6: with only a generic progress/status frame and no explicit `awaiting-input` signal, "the status badge reflects `chat-sessions`' RUNNING / NEEDS YOU state for the right node" and the matching AC are untestable beyond "the badge renders whatever `chat-sessions` reports" — which is the right seam for slice 6 to test against regardless, so recommend slice 6's criterion be worded as exactly that and the derivation correctness be tested in slice 5. (b) Slice 5's finding 7: with no transcript backfill, a canvas opened against already-running sessions renders correctly-positioned nodes with **empty** transcripts, which reads as a canvas bug and will be reported as one. ## Summary

The slice is feasible but is not currently buildable as written, for three independent reasons. **Sequencing:** the layout verdict is a hard gate on roughly half the criteria, the prototype has no host page (forcing the skill's own last-resort shape against fixture data) and no declared place to record its outcome — findings 1-3. **Size:** this is two slices, and the cut is already implied by the file list — `chat-node.ts` plus the page is verdict-independent, `chat-canvas.ts` is the part the verdict gates and the part that can be deferred without losing a usable workspace — finding 4, which also re-points slice 9's dependency. **Boundaries:** the composer's manifest affordances belong to slice 8, not here (19); one of slice 6's zero-states is currently an acceptance criterion on slice 4 (20); "closing a node" is undefined and used two ways (21); and three unresolved slice-5 escalations determine how this slice receives its data at all (22).

The technical questions all resolved cleanly and with evidence. Rendering: DOM plus one transformed container, no dependency, no shadow root, with named failure modes at scale (5-9). Theme: `style.css` is importable from a second entrypoint with zero duplicated Tailwind output — verified in the built artifact — but its global `body` rule must be escaped with a fixed-position board root rather than edited, since it lives in slice 9's glob (10, 11); `ui-helpers.ts`'s `ACCENT` should be left alone and the hex-scan criterion scoped to slice 6's own files (12). Position state belongs in `chrome.storage.local` on the repo's existing key convention, which introduces no undeclared dependency but makes the persistence promise good only within one daemon lifetime (18). Testing: happy-dom has no layout engine, so geometry must be tested through exported pure functions (16), while `prefers-reduced-motion` is genuinely mechanizable provided it is read from JS rather than honoured only in CSS (17).

Two items are the human's: the linear-view question in 13, and the meaning of "close a node" in 21. Finding 13's WCAG 2.5.7 half is not a judgment call — a non-drag pointer alternative is required at AA and the plan promises only the keyboard half.
