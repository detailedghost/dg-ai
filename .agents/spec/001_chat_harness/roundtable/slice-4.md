# Slice 4 — extension-marker-and-background

Per-slice review findings (plan.md step 5).

1. [COMPLETENESS/AMBIGUITY] `chrome.storage.session` is not exposed to content scripts by default in either Chrome or Firefox — Chrome's own docs state session storage "is not exposed to content scripts by default" and is "specifically recommended for use within service workers," restricted to trusted contexts unless `setAccessLevel` is called (nothing in the plan calls it, and nothing should — see below). The engineering bullet "On marker capture, store the port, token, and sessionId in chrome.storage.session and open the chat page" does not say which script performs the write, and a naive reading (do it inside `chat-marker-capture.content.ts`) will throw at runtime. The write — and the `browser.tabs.create`/reopen call, which content scripts also cannot make — must happen in the background (`lib/background/chat.ts`'s `registerChat`), with `chat-marker-capture.content.ts` only parsing + stripping the marker and relaying the payload to the background over a new `lib/chat-messages.ts` MSG key. This is almost certainly the intended design (it's exactly why both `chat-messages.ts` and `registerChat` are separate deliverables on this slice), but the plan text should say so explicitly so whoever implements it doesn't reach for the direct-write shortcut. No `setAccessLevel` elevation is needed or wanted — routing through the background is both correct and sufficient.

2. [FEASIBILITY — confirmed] A content script matched only to `http://127.0.0.1/*` is valid and WXT-supported via `defineContentScript`'s `matches` field, exactly like the existing `demo-marker-capture.content.ts` (`matches: ["<all_urls>"]`). Chrome match patterns ignore port numbers entirely — Chrome's docs contrast this explicitly against *content setting* patterns, which "can specify a port number," implying ordinary match patterns cannot and instead match all ports. So `http://127.0.0.1/*` matches the daemon's OS-assigned port regardless of value, on both browsers.

3. [FEASIBILITY — confirmed, no `localhost` needed] Nothing in the plan ever constructs a `localhost`-hostname bootstrap URL — slice 2's engineering and acceptance criteria consistently print/open `http://127.0.0.1:<port>/start` (literal IP), and `localhost` appears nowhere in plan.md. `http://127.0.0.1/*` alone is sufficient; no `http://localhost/*` entry is missing.

4. [MANIFEST — confirmed necessary and correctly scoped] On Chrome, a manifest-declared `content_scripts` entry is auto-granted injection from its own `matches` field with no separate `host_permissions` entry required — Chrome's own manifest example shows a content script with `matches` and no `host_permissions` at all — and Chrome's branch already carries `<all_urls>`, a superset, so no Chrome-side change is needed. On Firefox, this is genuinely different: Firefox Extension Workshop's MV3 migration guidance is explicit that host permissions used by `content_scripts.matches` must also be declared in `host_permissions` (both are shown together in the install/grant prompt from Firefox 127). The Firefox branch in `wxt.config.ts` currently emits `{}` for this whole options object (`firefox ? {} : {host_permissions: [...], content_security_policy: {...}}`), so Firefox today has zero `host_permissions`. The plan's fix — add `host_permissions: ["http://127.0.0.1/*"]` under the Firefox arm — is required, not optional, and is structurally independent of the separate `browser_specific_settings.gecko` spread and the top-level `permissions` array (which already lists `"storage"` for both browsers, covering `storage.session`'s permission requirement). No collision with either.

5. [PLATFORM SUPPORT — confirmed clean] `chrome.storage.session` shipped in Chrome 102 (2022). Firefox shipped it in Firefox 115 (2023; landed per Bugzilla 1687778, and confirmed to work under both MV2 and MV3, not MV3-only). Firefox 139 is comfortably past that floor. Both browsers restrict the API to trusted (extension-page) contexts by default with a 10MB quota — consistent across browsers, and consistent with finding 1's requirement that only the background script touch it.

6. [DESIGN CHOICE — confirmed sound] Session storage's "cleared on browser restart, memory-only" lifetime fits this payload well: the daemon's OS-assigned port and minted token are already tied to a single daemon process (idle-TTL'd per slice 2), so they're meaningless after a browser restart anyway, and keeping the token out of disk-backed `storage.local` is a real, if modest, security improvement — the token never touches the extension's on-disk storage. No change needed.

7. [TOKEN HANDLING — confirmed clean, no new risk] The token lives in a URL fragment, which is never transmitted to the server (fragments are client-side only) regardless of the daemon's plain-HTTP loopback listener. `document_start` content scripts are guaranteed to run before the page's own scripts execute, and the plan's "strip the marker after acting, matching how the demo and proto markers behave" bullet points at the existing `captureMarkerEarly` convention, which calls `history.replaceState` *before* awaiting anything specifically so a page router can't replay the marker. Following that same order removes the fragment from the tab's live history entry, which is also what session-restore reads from afterward. This is the same architecture and same accepted risk profile as the existing `_demo`/`_proto` markers — slice 4 introduces no new leak vector beyond what the codebase already ships and accepts.

8. [SIBLING DISJOINTNESS — confirmed clean] Diffed slice 4's file list against slices 1, 6, and 9: no path overlaps. Slice 1 touches only `pkg/common/**`. Slice 6's `entrypoints/chat/**` is a sibling directory to slice 4's `entrypoints/chat-marker-capture.content.ts` and `entrypoints/background.ts`, not nested under either, and needs no `wxt.config.ts` edit — confirmed by the existing `entrypoints/review/` page, which has zero mentions in `wxt.config.ts` today (WXT auto-discovers entrypoints/ pages from the filesystem). Slice 9's `pkg/extension/entrypoints/options/**` edits the pre-existing `options/` page in place and likewise needs no manifest touch. Slice 4 is the only slice in this bundle that touches `wxt.config.ts` or `entrypoints/background.ts`.

9. [STRUCTURE CONFORMANCE — confirmed clean] `utils/chat-marker.ts` as its own module (not folded into `demo-marker.ts` or the generic `marker.ts`), `lib/chat-messages.ts` as a sibling to `demo-messages.ts` (not an addition to it), and `lib/background/chat.ts` exporting `registerChat` re-exported from `lib/background/index.ts`'s barrel and invoked from `entrypoints/background.ts`'s `defineBackground` — all directly mirror the established one-module-per-marker-key and per-feature-`registerX` conventions already in the codebase (`demo-marker.ts` + `demo-marker-capture.content.ts`; `registerProto`/`registerRecording`/`registerTabGrouping`/`registerTourState`). No structural friction.

10. [MINOR RECOMMENDATION] `registerChat` should accept an injectable seams/options parameter mirroring `registerProto`'s `RegisterProtoOptions` (`options.browserApi ?? browser`), rather than reaching for `globalThis` patching, so `background-chat.spec.ts` can mock `tabs.create`/`storage.session` the same way `proto-background.spec.ts` mocks its browser calls. Not a plan defect — an implementation note for whichever engineer picks this up. Test feasibility is otherwise already proven by the existing suite: `__tests__/wxt-config.spec.ts` already imports `wxt.config.ts` and asserts per-browser `host_permissions` directly (extending it, or adding a slice-4-owned assertion, needs no new test infrastructure), and `__tests__/proto-content.spec.ts` already shows the pattern for stubbing `defineContentScript`/`location`/`history` to test a marker-capture content script the same way `chat-marker.spec.ts` will need to.
