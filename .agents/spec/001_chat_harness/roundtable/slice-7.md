# Slice 7 — agent-facing-cli

Per-slice review findings (plan.md step 5).

1. [OPEN — escalate] How does the CLI reach the daemon, and how does it get the session token? — Slice 2 only stands up a WebSocket (page transport) plus HTTP for `/start` and asset serving (plan.md:93-94); nothing in slice 2's or slice 7's Engineering bullets names a CLI-facing surface. Slice 7's own Testing Criteria ("send and status produce frames that validateChatFrame accepts") confirms the CLI constructs real `ChatFrame` objects, so the wire *format* is settled — but the *mechanism* is not: does `recv`/`send`/`status`/`spawn` each dial a fresh short-lived WebSocket to the same loopback server (reusing slice 2's session-create handler, which today is written for "a connected page"), or does the daemon expose a separate local-only HTTP surface (e.g. a long-poll `GET` for `recv --block --timeout`, which is arguably the more natural fit for a one-shot process than a WS handshake)? Whichever is chosen, the CLI needs the per-session token to attach to frames/requests, and neither slice specifies where that token is persisted for the CLI to read or what permissions guard it. Slice 2/3 already set precedent for this exact class of secret (`~/.dg/key` at mode 0600); recommend the session token file follow the same 0600 precedent, but the *mechanism* is a one-way door affecting the whole shape of `src/commands/**` and the local-privilege threat model (any other process running as the same OS user could otherwise read the token and inject/read messages), and it belongs in Code Structure, not decided ad hoc by slice 7. Options: (a) CLI opens its own WebSocket per invocation, speaking the same ChatFrame protocol as the page; (b) daemon exposes a small local-only HTTP surface (long-poll for `recv`) that internally builds/validates ChatFrames server-side. Recommendation: (b) — a one-shot process doesn't need WS keepalive/reconnect machinery, and HTTP long-polling is the idiomatic way to implement `--block --timeout`; the standing-WebSocket case only exists for the persistent multi-session page.

2. [CONTRACT] Result convention conflicts with slice 7's own text — Code Structure's "Result convention" decision (plan.md:464-469, applies to slice 7) states "the agent-facing CLI throws and exits non-zero the way `pkg/skills-cli/src/index.ts` does," matching the repo-wide precedent (every `process.exit` in `pkg/skills-cli/src` is 0 or 1; `index.ts`'s top-level `.catch` uniformly exits 1 — verified, no distinct exit codes exist anywhere in the codebase today). But slice 7's Engineering/Testing/Acceptance repeat, three times, that timeout must be "a distinct machine-readable timeout result **rather than an error exit**" with "a distinct exit code." These directly contradict: the Code Structure decision as written gives `recv` no room for a third outcome. Recommend the plan carve out an explicit exception: `recv --block --timeout` has three outcomes, not two — exit 0 (message delivered), a reserved non-1 code for timeout (bypassing the thrown-Error path entirely, e.g. a direct `process.exit(N)` in the action handler before any throw), and exit 1 for every other failure (dead daemon, bad `--session`, validation failure) via the existing throw-and-exit convention. Without this written down, slice 7 and slice 10's SKILL.md (which documents "the exit codes") risk being written against different assumptions.

3. [CONTRACT] Single `--timeout` conflates two different waits — "recv against a dead daemon fails with a clear message rather than hanging" (Testing Criteria) implies a fast failure, but the only exposed knob is `--timeout <seconds>`, which Acceptance Criteria uses for values like 300s of *message*-waiting. If connection establishment and message-waiting share one deadline, a dead/unreachable daemon either hangs for the full message-wait timeout before failing (contradicting "rather than hanging") or the implementation quietly needs a second, undocumented, short connect-timeout. Recommend the plan state explicitly that connecting to the daemon is bounded by its own short fixed timeout (fails fast, exit 1, distinct from the timeout result), independent of the `--timeout` value governing how long `recv` waits for a message once connected.

4. [DELIVERY] Peek vs. consume-then-emit ordering is unspecified, and slice 3 doesn't yet expose what's needed — The parent's framing question: does `recv` acknowledge-and-consume or peek? Slice 7 only requires messages be "durably stored before recv reports it delivered" (write-side durability) and slice 3 only promises "a message sent while no agent is listening is delivered by the next recv" (no reader present yet). Neither addresses the read-side crash window: if `recv` dequeues/marks-consumed in the store *before* successfully writing the message to stdout, a crash of the CLI process in between (broken pipe, OOM-kill, host restart) loses that user message permanently — with no re-delivery, since the store already considers it consumed. Compare to slice 5's outbound direction, which explicitly guarantees exactly-once delivery across reconnects; this inbound direction has no equivalent guarantee, and duplicate delivery (at-least-once) is far less harmful here than silent loss. Recommend: `recv` should fetch without consuming, write to stdout, flush, and only then mark the message consumed (accepting an occasional duplicate on crash, never a drop) — and recommend slice 3's store expose a peek/ack (or cursor-based) read API rather than an atomic pop, since its current table list (sessions, messages, status_events, assets, command_invocations) and Engineering bullets don't yet specify which of the two it provides.

5. [SESSION] `--session` cwd-matching is underspecified for the ambiguous cases — Three concrete gaps in "defaulting to the session whose cwd matches the invocation" (plan.md:312): (a) two live sessions share a cwd (e.g. two `dg:start` runs from the same repo) — no tie-break rule is given; (b) the invocation's cwd matches no registered session (e.g. agent `cd`'d into a subdirectory, or the session was registered from a parent directory) — no documented fallback; (c) cwd stability is not defined under worktrees/symlinks — is the comparison a literal string match, or resolved via `realpath` on both the registration side (`dg-server start`) and the lookup side (`recv`/`send`)? Silently guessing wrong in any of these routes a message into the wrong repo's chat, which is a correctness/isolation problem, not just a UX one. Recommend: on ambiguity (zero or multiple matches) `recv`/`send`/`status` should error listing the live sessions and their cwds and require an explicit `--session`, never guess; and cwd comparison should use `realpath` on both sides, mirroring the `realpath`/`isContainedBy` pattern already used in `pkg/skills-cli/src/commands/proto.ts`'s `ensureSafeAnswerPaths`.

6. [MANIFEST] No CLI verb covers "manifest changed mid-session, republish" — Slice 7's verb list is only `recv`, `send`, `status`, `spawn` (plan.md:307-312), yet Engineering also requires "Publish the manifest to connected pages on registration **and on change**" and slice 7 owns `pkg/dg-server/src/manifest/**` as a real directory. There is no declared command for supplying an updated manifest after the initial hand-off, and nothing describes daemon-side file-watching of the original path either (no such watcher is scoped anywhere in slices 2 or 7). As written, "on change" has no trigger. Recommend adding an explicit manifest verb (e.g. `dg-server manifest --session <id> <commands.json> <subagents.json>`) to slice 7's Engineering list, or clarifying that `spawn`/re-running the manifest flags on an already-registered session is the re-publish path.

7. [MANIFEST] Manifest persistence has no home, and path resolution needs to happen in the CLI's own cwd — Two related gaps: (a) the daemon must retain the *validated* manifest content for the lifetime of the session so it can (re-)publish it to a page that connects or reconnects later — re-reading the original file path at that later point is unsafe, since scratch-dir manifest files may no longer exist — but slice 3's table list (sessions, messages, status_events, assets, command_invocations; plan.md:189) has no manifest storage, so there's nowhere for slice 7 to persist it through its dependency on slice 3; (b) mirroring the `proto plant` idiom, a relative manifest path argument must be resolved against the *CLI process's* cwd before it crosses to the daemon — the daemon is a long-lived process reused across sessions (per slice 2's "reuse a live daemon" bullet) and its own `process.cwd()` has no relationship to whichever repo invoked this particular command. If the raw string is forwarded and the daemon does `readFile(path)` itself, relative paths will resolve against the wrong directory essentially always. Recommend flagging (a) back to slice 3 for a manifest-storage column/table, and stating (b) explicitly in slice 7's Engineering: resolve manifest paths to absolute in the CLI before sending.

8. [STRUCTURE] Slice 2's file glob collides with slice 7's (and slice 3's) test directories — Slice 2 declares `pkg/dg-server/__tests__/**` unscoped (plan.md:20), which is a strict superset of slice 7's `pkg/dg-server/__tests__/commands/**` and slice 3's `__tests__/store/**` / `__tests__/crypto/**`. As written, every test file under this slice's ownership also matches slice 2's declared file list. Recommend narrowing slice 2's glob to something like `__tests__/{server,session,utils}/**`, mirroring its own `src/` subdirectories, so slice 2/3/7 test ownership is actually disjoint. (Noting this per the review brief rather than editing plan.md — routes to whoever owns slice 2's file list.)

9. [STRUCTURE] No declared file home for CLI-side daemon-connection plumbing — Slice 7's files are only `src/commands/**` and `src/manifest/**`. Whatever transport is settled in finding 1 (WS client or HTTP long-poll client, token loading, frame construction/validation glue shared across `recv`/`send`/`status`/`spawn`) needs a home that isn't one of the four command files. `src/utils/**` is slice 2's, not slice 7's, per the file list. Recommend either keeping this plumbing as a non-exported helper module inside `src/commands/**` (e.g. `src/commands/client.ts`), or explicitly noting in Code Structure that slice 7 extends slice 2's already-merged `src/utils/**` for this one shared concern.

10. [LIFECYCLE] Idle-TTL self-exit isn't reconciled with a long blocking `recv` — Slice 2 requires "idle-TTL self-exit so no daemon is orphaned" but never defines what counts as activity. `recv --block --timeout` can legitimately hold a connection open for minutes while a human types (Acceptance Criteria uses 300s as an example). If the idle timer only resets on frame traffic, a daemon could self-exit while an agent is validly blocked inside `recv`, turning what should be a clean timeout result into a confusing dropped-connection error instead. Recommend stating explicitly that an open blocking `recv` (for whichever slice-2 transport is chosen) counts as activity for the idle-TTL clock for its full duration.

11. [MINOR] `spawn` should reuse slice 2's session-create registration path, not duplicate it — Slice 2 already implements "Handle a session-create frame from a connected page... returning the new session's id and token" (plan.md:157); slice 7's `spawn` needs the identical daemon-side operation (register a session, optionally with an agent identity), just triggered from the CLI instead of a page. Once finding 1 settles how the CLI reaches the daemon, recommend `spawn` invoke that same registration handler rather than growing a second one — low risk, just worth stating so it isn't re-derived independently.
