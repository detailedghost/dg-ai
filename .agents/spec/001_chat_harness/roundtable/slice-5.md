## Findings

1. **[BOUNDARY] `chat-transcript.ts`'s headless line is achievable, but only if it never touches presentation** — the repo has two different DOM-rendering conventions and slice 5 must pick the *other* one from the obvious-looking precedent. `demo-tour.ts`/`picker.ts` inject Shadow DOM + inline CSS-custom-property theming (`injectTheme`, `DEMO_THEME_CSS`) because those overlays paint on top of arbitrary third-party pages and need bleed isolation. The chat page (`entrypoints/chat/`, slice 6) is a normal top-level extension page like `entrypoints/review/` and `entrypoints/options/`, which use a real stylesheet with semantic classes (`.panel`, `.btn`, `.neon-title`, CSS custom properties in `style.css`) — no Shadow DOM, no inline styles. If `chat-transcript.ts` follows the demo-tour precedent (inline styles, hard-coded hex like `ui-helpers.ts`'s `ACCENT`), slice 6's own testing criterion ("assert no hard-coded hex colors outside style.css") forces a rewrite of everything slice 5 rendered — exactly the failure mode the task asked me to watch for. Recommendation: `chat-transcript.ts` must emit plain DOM/class-hooked markup only (e.g. `dg-chat-message`, `dg-chat-message--agent`, `dg-chat-message--user`) with zero inline styles and zero positioning/drag logic, returning a container element or accepting one to mount into. Slice 6's `chat-node.ts` then supplies 100% of the visual styling via `style.css` and wraps the returned element in its own draggable chrome. This is achievable and should be written down explicitly as the render contract, not left implicit.

2. **[BOUNDARY] `chat-sessions.ts`'s "unread count" needs an explicit read/focus signal that no slice declares** — unread state requires the module to know when a session is "being viewed," which is a slice-6 (canvas/node-focus) concept. Recommend slice 5 expose a narrow `markSessionRead(sessionId)`-shaped method rather than inferring read state itself, so the dependency on slice 6 is an explicit function call, not an assumption baked into either module.

3. **[OPEN — escalate] Exactly-once delivery has no mechanism behind it** — the acceptance criteria promise a message typed while disconnected is delivered exactly once on reconnect, and the testing criteria add "does not duplicate already-acknowledged messages." Slice 1's declared frame list (user message, agent message, progress/status, command invocation, command result, manifest publish, session list, session create, session closed, error) contains no client-generated message id and no ack frame; slice 1 only requires every frame to carry `sessionId` + session token, not a per-message idempotency key. Without one, a resend after a lost ack either duplicates (server can't tell it's the same message) or the client must guess it was received (unsafe). Slice 5 cannot build the outbox/reconnect-flush logic its own testing criteria demand without this. Options: (a) add a client-generated message id to the "user message" frame plus a daemon-side ack frame and idempotent insert (slice 3's `messages` table already has an `ids` column — needs to accept/dedupe on a client-supplied id) — this is the only option that actually delivers "exactly once"; (b) settle for at-least-once with UI-level dedup by id (weaker than the stated AC, would need the AC reworded). Recommend (a), which requires changes to slices 1, 2, and 3 that no slice currently scopes. This blocks slice 5's own stated testing criteria as written.

4. **[OPEN — escalate] Where the client runs is undecided in slice 5's own text, but the Code Structure section's own dependency list answers it — and the implications aren't scoped anywhere.** Plan.md never states whether `chat-client.ts`'s WebSocket lives in the chat page (slice 6's tab) or the MV3 background service worker (registered via slice 4's `registerChat`, alongside `registerTabGrouping`/`registerRecording`/`registerProto`/`registerTourState`). This matters concretely: a page-owned socket dies when the chat tab closes, silently ending "background chats keep receiving while the chat tab is shut" — a headline feature (Purpose: "can spawn additional background chats bound to different agents"). Evidence the plan intends background-owned: the Code Structure "In-browser IPC keys" decision lists `chat-messages.ts`'s `MSG` object as applying to **slices 4, 5, and 6** — that only makes sense if slice 5's client needs cross-context (`chrome.runtime`) messaging, which a same-page module would never need (page-context modules call each other directly; `demo-tour.ts` only reaches for `MSG` because it's a content script talking to the background service worker). But no slice — 4, 5, or 6 — has an Engineering bullet assigning "background holds the socket, relays demuxed frames to open chat page(s) via `chrome.runtime.connect` + `MSG`". Recommendation: make the background-owned design explicit (a new `registerChatClient`-shaped hook in slice 4 or 5, wired through `lib/background/index.ts`), and add the missing relay bullet to whichever slice owns it. This is a one-way-door architecture call that changes both slice 4's and slice 6's file responsibilities — needs a human decision, not a slice-5-engineer guess.

5. **[FINDING, backs #4] MV3 WebSocket-in-service-worker survival is real but conditional — verified via context7, not memory.** Chrome 116+ lets a service worker keep a WebSocket alive past its normal ~30s idle-suspend window, but only if the extension (a) declares `minimum_chrome_version: "116"` in the manifest, and (b) exchanges a message (e.g. a ping) at an interval under 30s (Chrome's own docs recommend 20s) for the entire time the socket must stay open. `pkg/extension/wxt.config.ts` (owned by slice 4) currently sets no `minimum_chrome_version`. If finding #4 resolves to background-owned, slice 5 needs: a keepalive ping every ~20s in `chat-client.ts` while connected, a corresponding testing criterion (currently absent — the testing criteria mention backoff/reconnect but nothing about keepalive cadence), and a manifest bump that isn't currently assigned to any slice's file list. Note also: even with keepalive, a service worker can still be evicted by browser restart, extension reload, or Chrome forcibly reclaiming memory — "background chats always keep receiving" cannot be an absolute promise regardless of where the socket lives, which strengthens finding #7 below regardless of how #4 is resolved. I did not find Firefox-specific facts on this via context7 — worth a follow-up if Firefox parity for background-owned sockets matters, since the plan's Firefox host-permission handling implies both browsers are in scope.

6. **[OPEN — escalate] Status derivation (RUNNING / NEEDS YOU) has no explicit signal to derive from.** Slice 1 covers a single generic "progress/status" frame type; nothing in slice 1 or slice 7 (the agent-facing CLI) declares an explicit "the agent is now blocked on `recv`" signal distinct from "a turn is in flight." Slice 5's own testing criterion — "Status resolves to NEEDS YOU when the agent is awaiting input and RUNNING while a turn is in flight" — cannot be implemented correctly from absence of frames alone: a long $-command execution (slice 8) or a quiet agent turn would be indistinguishable from NEEDS YOU under a timeout/silence heuristic, and a wrong inference here is exactly the kind of externally-visible bug the acceptance criteria are trying to prevent. This is a slice-1 (frame shape) and slice-7 (CLI must emit the signal when `recv --block` starts waiting) gap, not something slice 5 can fix internally. Recommend slice 1's status frame carry an explicit `state: "running" | "awaiting-input"` (or equivalent) field, with slice 7's `recv` emitting it on entering the blocked wait.

7. **[OPEN — escalate] No inbound history/backfill mechanism exists for a client that connects (or reconnects) mid-session.** The exactly-once guarantee slice 5 must build (finding #3) only covers *outbound* messages composed while disconnected. Nothing covers the *inbound* direction: an agent's replies that arrive while no page/socket is attached to a session (chat tab closed, background service worker suspended, or a fresh tab opened against an already-running session). Since Dexie/IndexedDB chat persistence is explicitly excluded from scope and the in-page session/transcript objects are the mirrored, non-durable twin (per the Code Structure "Session handle representations" decision), the browser side has no local record of messages that happened while disconnected — even though slice 3's SQLite store has them. Slice 1's frame list has no "replay transcript since X" or "session history" frame, and slice 5's "session list" frame (per its Engineering bullets) is not documented to carry recent transcript content, only session metadata. Recommend adding a transcript-backfill mechanism (either `session list` returns each session's recent message history, or a dedicated request/response frame) — currently unassigned to any slice, and slice 5 depends on it existing to make its own transcript rendering trustworthy across reconnects.

8. **[OPEN — escalate] Daemon restart can change the port slice 5 needs to reconnect to, and nothing lets the browser rediscover it.** Slice 2 binds "an OS-assigned port" — ephemeral, not fixed — and slice 4 captures a snapshot of `port`/`token`/`sessionId` into `chrome.storage.session` once, at marker-capture time. Slice 5's own Acceptance Criterion says "Given the daemon is stopped and restarted, when the page stays open, then the client reconnects without a reload" — but if the daemon process actually restarts (crash, not just a network blip), it gets a new OS-assigned port, and nothing refreshes `chrome.storage.session` afterward. Native messaging (the one channel that could read the `~/.dg` lockfile from the browser side) is explicitly excluded from scope. As written, slice 5's exponential-backoff reconnect will retry against a now-dead port forever after a real daemon restart, and no slice provides a rediscovery path. Options: (a) the daemon prefers to rebind its last-known port on restart when free, falling back to OS-assigned only on conflict (a slice-2 change); (b) the AC is narrowed to cover only same-process disconnects (network blip / daemon hang, not full restart), leaving "daemon restarted on a new port" requiring a fresh `dg:start` marker capture — a real product-behavior change from what's currently promised. This is a cross-slice (2 + 5) contradiction that needs a human call, since it changes either slice 2's port-binding guarantee or slice 5's acceptance criterion.

9. **[MINOR] Inbound frame validation isn't in the testing criteria.** Slice 5's demux bullet says to drop frames for unknown `sessionId`s, but nothing says to run every inbound WebSocket payload through slice 1's `validateChatFrame` before acting on it. Loopback-only reduces but doesn't eliminate the risk of a malformed/truncated frame crashing the page mid-session. Recommend adding "a malformed inbound frame is rejected/logged rather than thrown past the demux" as an explicit testing criterion, reusing the validator slice 1 already builds.

10. **[MINOR] Reconnect backoff should specify jitter.** "Exponential-backoff reconnect" is stated, but a single daemon restart could make every open chat tab across every repo (single-daemon-many-sessions, per slice 2) reconnect on the same backoff schedule simultaneously. Recommend adding jitter and stating it as a testing criterion, not just leaving it to engineer discretion.

11. **[AMBIGUITY, non-blocking] Session-token scope is unclear.** Slice 1 says every frame carries `sessionId` + "the session token" (singular, per-session, minted at registration), and slice 4 stores one `port`/`token`/`sessionId` triple in `chrome.storage.session`. But slice 5 is expected to demultiplex frames for *many* sessions over one socket, and slice 6's canvas shows *all* live sessions at once. If tokens are strictly per-session, a page holding only one token has no declared way to see other sessions; if any valid token authorizes full multi-session visibility (plausible given the loopback, single-user trust model), that should be stated rather than left implicit, since it directly determines what `chat-client.ts`'s connect handshake needs to send. Not blocking — flagging so slice 2/5 engineers make the same assumption.

12. **[CLEAN] Sibling disjointness confirmed.** No filename or declared-responsibility overlap between slice 5's `chat-client.ts`/`chat-sessions.ts`/`chat-transcript.ts` and slice 6's `chat-canvas.ts`/`chat-node.ts` or slice 8's `chat-autocomplete.ts`. Slice 6's `chat-node.ts` "showing... transcript" is consistent with mounting slice 5's rendered output as a subcomponent (see finding #1); slice 8's autocomplete and slice 6's composer are both outside slice 5's declared headless scope, which slice 5's own Engineering bullets correctly exclude ("Keep this slice headless — no DOM layout beyond the transcript renderer").

13. **[CLEAN] Structure conformance.** Declared test paths (`pkg/extension/__tests__/chat-client.spec.ts` etc.) match the established flat `__tests__/*.spec.ts` convention already used by `demo-recorder.spec.ts`, `tab-grouping`-adjacent specs, `browser-support.spec.ts`, etc. — no new layout introduced. Reuse of `createSerialQueue` from `@dg/common` for the outbox (per the Code Structure "Outbound frame ordering" decision) is correctly scoped to slice 5 and matches the one existing queue primitive in the repo — no local reimplementation risk.

## Summary

This slice's core promise — "headless" state/logic with a thin transcript renderer — is structurally achievable (findings #1, #12, #13), but four of the six areas the task asked me to press on surface real cross-slice gaps that slice 5 cannot close by itself: exactly-once delivery has no id/ack mechanism (#3), the socket's home (page vs. background) is implied but unstated and carries concrete MV3 keepalive/manifest requirements (#4, #5), status derivation lacks an explicit signal (#6), inbound backfill after a disconnect is entirely unaddressed (#7), and daemon-restart port rediscovery is unsolved (#8). Findings #3, #4, #6, #7, and #8 should go to the human before slice 5 implementation starts — several require changes to slices 1, 2, 3, or 7, which slice 5 depends on but does not own.
