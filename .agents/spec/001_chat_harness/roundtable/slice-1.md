# Slice 1 — shared-contracts

Per-slice review findings (plan.md step 5).

1. [Reuse before building] Extract `fail`, `isRecord`, `requireRecord`, `requireString`, `requireFiniteNumber`, `requireStringArray`, `requireStringRecord` out of `pkg/common/src/proto-format.ts` (currently module-private, unexported) into a small shared internal module, e.g. `pkg/common/src/assert.ts`, and have both `proto-format.ts` and the new `chat-format.ts` import from it — rather than `chat-format.ts` redeclaring its own private copies of the same primitives. This is exactly the case the project's "shared utilities, not local ones" rule calls out: a second sibling module wants the identical helper. **Scope note:** this requires editing `pkg/common/src/proto-format.ts`, which is not in slice 1's declared `files` list. Recommend adding `pkg/common/src/assert.ts` and `pkg/common/src/proto-format.ts` to slice 1's file list before engineering starts (no other slice touches `proto-format.ts`, so this carries no cross-slice file-overlap risk).

2. [Reuse before building] Reuse the already-exported `validateProtoIdentifier` (barrel-exported from `proto-format.ts` today) for the "rejects an unknown subagent name shape" check on session-create frames, instead of writing a second identifier-grammar regex. The subagent names already in use in this repo (`js`, `security`, `qa-code`, `design`, …) fit `PROTO_IDENTIFIER`'s grammar directly; call it with a different `path` label (e.g. `"agent name"`) for the error message. This needs no scope change — `validateProtoIdentifier` is already importable from within `chat-format.ts` as a sibling module.

3. [Completeness — Contracts gap] Slice 2's Testing Criteria says a `dg-server start` "prints a marked bootstrap URL parseable by the slice-1 validator," but slice 1's own Engineering checklist only commits to a session-handle **type** ("do NOT reuse it for the in-page object") — no validator function is named. Recommend slice 1 add an explicit `validateSessionHandle` (name TBD) alongside the type in `chat-format.ts`, plus a Contract test for it, mirroring how `demo-marker.ts`/`proto-marker.ts` on the extension side already import `validate`/`validateProtoPlan` from `@dg/common` to check a decoded marker payload. Without this, slices 2 and 4 have no agreed function name to import when they parse the bootstrap marker and lockfile.

4. [Ambiguity — protocol design, needs tightening] The blanket rule "every frame carries sessionId and the session token; validateChatFrame rejects a frame missing either" is in tension with a `session create` **request** frame for a session that doesn't exist yet — there is no token to attach for something not yet created. The likely resolution: `session create` is only ever sent over an *already-authenticated* session's socket (the outer `sessionId`/`token` belong to the requesting session), carrying the new session's id/token back in a nested field on the response; the very first session in a browser tab is minted only through the CLI + bootstrap-marker path, never through a `ChatFrame` at all. Recommend this be written down explicitly in slice 1's Engineering/Testing checklist (what the outer `sessionId`/`token` authenticate on a `session create` frame, and where the new session's token travels back) so slices 2, 5, and 7 don't each guess differently.

5. [Completeness gap — frame-type list] Slice 9's Engineering says to "reference [a staged asset] from the message that presents it," and its acceptance criterion has the chat node "render it from the loopback origin with no base64 in the transcript" — but slice 1's frame-type list has no attachment/asset-reference field on any frame type, including agent message. Recommend adding an optional attachment/asset-id field to the agent-message frame type now, with a Contract test, so slice 9 doesn't have to widen (and rename-cascade) the frame shape later.

6. [Risk — possible data loss, needs escalation] Engineering says the `~/.dg` resolver should honour `AI_SCRATCH_DIR` "the way `protoScratchPath` does" — i.e. fully override the root when set. `protoScratchPath`'s root is genuinely ephemeral agent-output scratch. The chat harness's `~/.dg` root is not: it holds the lockfile, the SQLite store of record (message durability while no agent listens), and the AES-GCM key file. `AI_SCRATCH_DIR` is documented elsewhere as scratch space "cleaned on reboot." Applying the same override to the daemon's persistent root means every one of those files vanishes on reboot whenever that env var is set (a routine dev-machine setting, not an edge case) — silently defeating slice 3's durability and key-continuity requirements.
   ⚑ RATIFY: Should `AI_SCRATCH_DIR` override the daemon's whole persistent root, override nothing on the persistent-state path (only apply to a genuinely ephemeral staging area, if any), or override only a documented non-durable subfolder? — Recommendation: do not let `AI_SCRATCH_DIR` affect the persistent root at all; keep persistent state pinned to `~/.dg` unconditionally.

7. [Ambiguity — path layout, needs tightening] "Per-OS defaults for Windows, macOS, and Linux" plus the acceptance criterion "returns that platform's documented default asset and data paths" reads as if the three platforms get genuinely different folder conventions (e.g. `%LOCALAPPDATA%`, `~/Library/Application Support`, XDG). But slice 10 already commits `bootstrap.ps1` to installing binaries into a literal `~/.dg/bin` on Windows too, and `protoScratchPath` already sets the precedent of one uniform `.dg` dotfolder under `homedir()` on every platform. Recommend slice 1's checklist say explicitly: one uniform `.dg` folder name under `homedir()` on all three platforms, matching slice 10 and `protoScratchPath`; "per-OS" refers only to resolving `homedir()`/`env` correctly per platform via injected seams, not to picking different OS-conventional directories. Also recommend naming the exact shape the resolver returns (e.g. explicit `lockfilePath`/`dbPath`/`keyPath`/`assetsDir` fields vs. a bare root string other slices join filenames onto) so slices 2, 3, and 9 don't each invent different property names.

8. [Structure conformance — verified, no issue] Confirmed via `grep -rn "node:" pkg/common/src/` that nothing under `pkg/common/src/` imports a `node:` builtin today, so the `./node` subpath export is a clean net-new addition with no existing code to migrate.

9. [Structure conformance — verified, needs a sharper proof] Traced the actual containment mechanics for keeping `node:` out of the extension bundle. `pkg/extension/wxt.config.ts`'s Vite alias maps `"@dg/common"` to the literal `src/index.ts` file. The installed `@rollup/plugin-alias@6.0.0` (bundled inside `node_modules/vite/dist/node/chunks/node.js`) does prefix matching — `importee.startsWith(pattern + "/")` — so a stray `import … from "@dg/common/node"` in extension code *does* match this alias, gets rewritten to `.../src/index.ts/node` (not a real file), and fails to load — the Vite **build** does fail loudly on a leak. However, `pkg/extension/tsconfig.json` (and `pkg/skills-cli/tsconfig.json`) already declare a wildcard path mapping, `"@dg/common/*": ["../common/src/*"]`, which resolves that same import fine for `tsc --noEmit`. So `bun run --filter='./pkg/extension' lint` will **not** catch a stray `@dg/common/node` import — only an actual `bun run --filter='./pkg/extension' build` will. Recommend slice 1's acceptance criterion name that exact build command explicitly (today's plan only ever names `test`/`lint` for the extension package across slices 1, 4, and 6), since it's the one command in the whole bundle that actually exercises this load-bearing containment guarantee.

10. [Risk — same-layer file overlap] Slice 4's files (`pkg/extension/**` and friends) are fully disjoint from slice 1's (`pkg/common/**`). No overlap. (Also note: slice 4 declares `depends_on: [1]`, so it is sequenced after slice 1 regardless of file overlap — it does not actually run in the same wave as slice 1, which is the only slice with `depends_on: []`.)
