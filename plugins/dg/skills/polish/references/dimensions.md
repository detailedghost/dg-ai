# Dimensions (quality only — see Out of scope)

1. **Reuse** — duplicated logic that already exists elsewhere in the project or its shared/vendored libraries (per the global "Reuse before building" rule). Flag and replace with a call to the existing function/util. **Utility placement:** a local helper (formatting/escaping/parsing/date-time/env-var + config reading/small pure transform) that duplicates one in another module — or is generic enough a sibling module would want it — should be hoisted into the shared util module (`lib/`, `common/`, `util/`) and imported by both call sites, not redeclared locally. Genuinely single-use module-specific helpers stay put. (Canonical smells: the same `escape_md`/date-formatter copied into several tasks; a `ReadPositiveInt`/`ParseEnv`/`GetConfig*` private static helper redeclared in each feature's `*Config.FromEnv()` / model / settings file.) **Actively look for this** — don't only match against helpers you already know exist: when a changed file declares small private helpers (especially in config/model/settings files), grep sibling modules for the same shape before assuming it's single-use. A helper any sibling would want, sitting local, is a finding even if no exact duplicate exists *yet*.

1. **Simplification** — YAGNI violations: speculative generality, unused parameters/overloads, config knobs with a single caller, dead branches, chained/nested ternaries, over-abstraction nobody needs yet. Prefer the smallest thing that works. Includes early returns over else: flag `else` branches and nested if/else ladders that could flatten into guard clauses (`if (!ok) return; …` beats `if (ok) { … } else { … }`) — a preference to apply, not just note, same as the rest of this dimension.

1. **Efficiency** — obvious algorithmic or allocation waste introduced by the diff (e.g. `O(n^2)` where `O(n)` was available, redundant re-computation in a loop, unnecessary copies). Not a perf-profiling pass — only what's visible from reading the diff.

1. **Altitude** — code that doesn't match the abstraction level of its surroundings: a one-off inline block where the rest of the file uses a helper, a comment restating what the code does instead of why, inconsistent naming/formatting against the immediate neighborhood.

1. **Dead code we introduced** — newly-unused exports/helpers/parameters/imports, a branch the diff made unreachable, a function whose last caller the diff just removed, an old path the change superseded but left in place. Narrower than Simplification's dead-branches bullet: this is specifically code *this* diff orphaned, not pre-existing cruft. Cheapest to catch right now, before it calcifies and someone assumes it's load-bearing.

1. **Latest-feature appropriateness** — new code uses the current, idiomatic feature/API for the language and libraries in play, not a deprecated/superseded pattern or a hand-rolled version of something the runtime/library already provides. Where a third-party library or framework is involved, consult CURRENT docs via context7 MCP (`resolve-library-id` then `query-docs`) before flagging — don't trust possibly-stale training memory. Bar is "appropriately": flag clear deprecated/superseded usage, not stylistic preference churn.

1. **Hygiene** — lint violations, dead imports, project code style. Within the diffed files: run the *project's* linter/formatter for that language (not a personal hook) and clear its violations, remove unused/dead imports and `using`s, and conform to the project's established naming/ordering/formatting conventions. Use the project's own toolchain per language — Biome for TS/JS, `csharpier` + StyleCop analyzers for C#, `ruff` for Python, etc. — the same delegation-by-language already used to pick the owning agent.

1. **Preferred constructs** — apply, don't just flag, subject to the same judge-step YAGNI/anti-churn filter as everything above:

   - *Immutability*: prefer `readonly` fields, `init`/`required` properties, records over mutable classes for data, local `const`/`readonly`; avoid reassigning parameters or exposing mutable collection fields. Flag needless mutability the diff introduced.
   - *Keep things on the stack*: prefer stack-friendly patterns where it genuinely helps readability/efficiency — value types/`struct` for small short-lived data, `Span<T>`/`ReadOnlySpan<T>` and stack allocation over heap allocations in hot paths, a simple loop over unnecessary boxing/LINQ-allocation churn. Not a license for micro-opt churn.

1. **Comment bloat** — comments that restate the code, the identifier, or the test name, and multi-line blocks where one line carries the whole point. Keep only the *why* a reader cannot recover from the code itself: a non-obvious external contract, an ordering constraint and what breaks without it, a workaround plus its ticket. Delete the rest — an explanation that reads well in a PR description is usually not earning its keep in the source. Canonical smells:

   - A `<summary>`/docstring above a test that paraphrases the test name. If the name says `SittingExactlyAtCap_ShouldNotChange`, the summary saying "a user pinned exactly at their cap stays there" is dead weight.
   - The same background rationale copy-pasted onto every declaration a change touched. State it once, at the site where a reader is most likely to hit the surprise; the other sites get a pointer or nothing.
   - **Doc comments used to dodge a comment-length limit.** A tool that caps inline `//` blocks but exempts `///`/`"""`/`/** */` is trivially routed around by writing the same bloat as a doc comment. Length limits express intent, not syntax — a 5-line `<summary>` of prose is the thing the limit exists to prevent. Judge doc comments by the same standard.
   - **Any comment over 2 sentences, inline or doc.** That is a hard ceiling, not a guideline, and it binds independently of the line count — two lines packed with run-on clauses fails it. A third sentence means the comment turned into design rationale; cut it to the one surprise a reader hits here and move the rest to the module/model doc or the PR body.
   - Narration of the obvious (`// loop over the users`). A project's established scaffolding comments (`// Arrange` / `// Act` / `// Assert`) are convention, not bloat — leave them.
   - Structured API tags (`<param>`, `<returns>`, `@param`, `Args:`) are *not* bloat, however many there are. They document a signature. Prose is what to cut.

   Cheap check when scoping: `git diff <base> -U0 | grep -cE '^\+.*(///|// |#)'` against the size of the change. A ratio a reviewer wouldn't sit through is a finding on its own, before reading any individual comment.

   **Run `unslop` over the comment prose that survives the cuts above.** When the `unslop` skill is not installed, skip this pass and print one line saying so. Short is not the same as human: a two-line comment can still open with "Note that" or "It's important to" and read as generated filler. Invoke the `unslop` skill as `cleanup --report` — that mode flags AI patterns and changes nothing, which is what the Find phase needs. Feed it only the comment text from your file group, not the code. Each flagged comment becomes an ordinary comment-bloat finding (`{file, dimension: "Comment bloat", issue, suggestedFix}`) and goes through the Judge like any other, so a flag alone never edits the source. Do not use bare `unslop` or `rewrite` here: those rewrite the text, and the Find phase must not edit.

## Out of scope (redirect instead of doing it here)

- Correctness bugs, security issues, logic errors → the "reviewer" sub agent for bug checking and the "security" agent for security concerns
- Missing test coverage, always-passing assertions → `standard-test` skill / `dg:qa-writer` agent.
- Re-formatting untouched code, or fighting an auto-running formatter/pre-commit hook on the same files → don't duplicate the hook's job or re-run it under a different name. Hygiene (dimension 7) covers lint-clean/import-tidy state of the diffed files themselves, not a whole-file/whole-repo reformat.
- Anything requiring a design decision (renaming a public API, changing a data model) → surface it as a suggestion in the summary, don't apply it unasked.
